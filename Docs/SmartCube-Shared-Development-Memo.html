What is already built

  • The server code is in git for the first time. Passwords and API keys are kept out. You get appsettings.Example.json with placeholders and copy it to appsettings.json on your PC (that file is git-ignored).
  • Database changes travel as numbered scripts. You add Database\Migrations\001-add-invoice-table.sql, 002-... and so on. Each runs once, in order, on every database. If one fails on production it is rolled back and the deploy stops. 000-baseline.sql is the live structure as of today, with no customer data in it.
  • One-command production deploy. Takes the site offline, rebuilds, applies new database scripts, brings it back and checks it answers.
  • One-command pull from development. Shows me what's new (and flags any database scripts), asks before changing anything, and tags a restore point so a pull can be undone.
  • A "SmartCube (dev)" run profile in Visual Studio, so the server runs on http://localhost:5000 without IIS.
  • A developer guide (README-DEVELOPMENT.md) in the server code with the setup steps below and the rules.

Setting up your dev environment

  1. In your server clone, copy appsettings.Example.json to appsettings.json.
  2. Create your dev database, structure only, from the same folder in PowerShell: 
    .\Database\Apply-Migrations.ps1 -Server "(localdb)\MSSQLLocalDB" -Database SmartCubeDev -Create
    LocalDB comes with Visual Studio. SQL Server Express also works: use -Server ".\SQLEXPRESS" and match the connection string.
  3. Choose the SmartCube (dev) profile in Visual Studio and press F5. Register a test account on your own dev site at /site/register.html.
  4. In the app, click the Server: line on the sign-in screen and enter http://localhost:5000. Your dev app then talks only to your dev server.

Email sending and the Smart Scan key are blank in the example settings, so password-reset emails and Smart Scan don't work in dev unless you add your own.

Rules that keep it safe

  • Never change the live database by hand, and never edit a migration script that has already been pulled. Add a new numbered one.
  • Make scripts safe to re-run where you can (IF COL_LENGTH(...) IS NULL ALTER TABLE ...). Test each one on your dev database first.
  • Never commit appsettings.json, API keys, passwords, App_Data\ or Installers\.
  • Commit to the shared repository as often as you like. Nothing reaches users until I pull and release.

Where things stand

The TrueLayer client secret has moved to the server. The app now asks the SmartCube server to do the bank token exchange (POST /api/account/truelayer/token, signed-in users only), and the server keeps the secret in its appsettings.json under TrueLayer:ClientSecret. Your dev server needs its own value there for bank connections to work in dev; without it the app reports that bank connections aren't set up. Nothing is stored on the server: the bank tokens go straight back to the user's PC.

From now on, app and server changes go through you. I pull into production when we've agreed, test, and release.
